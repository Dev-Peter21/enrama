# C03 verification

Status: **implemented on develop, awaiting maintainer acceptance** on 2026-10-23.
[Issue #7](https://github.com/Dev-Peter21/enrama/issues/7) remains open.
The [accepted contract](../json-schema.md) defines behavior; the
[implementation plan](../superpowers/plans/2026-10-23-c03-json-schema.md) records scope.

## Delivered behavior

- `enrama.config.schema.generate_schema()` returns deterministic UTF-8 JSON bytes
  derived from EnramaConfig in validation mode, with a Draft 2020-12 declaration.
- The checked [v1 artifact](../../schemas/enrama-v1.schema.json) has local internal
  definitions/references, model-derived structure/default metadata, and no
  timestamp, machine path or live HEAD dependency.
- `uv run --locked python scripts/schema.py` regenerates the fixed artifact;
  `--check` is read-only and rejects missing/stale bytes. Paths derive from the
  helper location, not cwd. Nonregular/symlink targets and I/O failures fail
  without reporting success. No product CLI command was added.
- Quality CI explicitly checks schema drift; all six verification environments
  also exercise checked-artifact agreement through pytest.
- The pure generator module is included in wheel/sdist. The source distribution
  additionally carries the checked schema; the wheel has no duplicate JSON copy.
  Installed consumers exercise generation outside the checkout.
- Manual client copying, exact source/version provenance, same-client-commit
  updates and local VS Code associations are documented. No client updater,
  schema service, application extension or client rewrite is required.

C01/C02 validation is unchanged. The schema can accept runtime-invalid URLs,
languages, traversal paths or duplicate IDs; trimmed-length and strict numeric
cases can also differ. Those gaps have explicit tests and remain documented.
Schema validation does not fill YAML defaults or open client assets. No CLI,
site generator, release, PyPI publication or deployment was performed.

## Local tests actually executed

Baseline **439 passed**. Test-first execution observed the missing generation
API (4 failed/51 setup errors) and then the missing development helper (13 setup
errors). A final boundary probe then reproduced two FIFO hangs in write/check
mode; a regular-file guard corrected both with RED→GREEN subprocess tests.
Implementing those features yielded **509 passed** in the full suite:
**55 new schema cases** and **15 new helper cases**.

Executed commands:

```console
uv sync --locked
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy src tests scripts
uv run --locked python scripts/schema.py --check
uv run --locked pytest --junitxml=reports/pytest.xml
uv build --python 3.12 --build-constraint build-constraints.txt --require-build-hashes
```

Coverage includes independent minimal/expanded examples, required/null/default/
unknown/type/version/catalog/pattern/list/length behavior, complete internal
references, deterministic committed bytes, source metadata/dynamic-default
honesty, and representative intentional schema/runtime differences. Helper
subprocesses exercise write/check behavior from unrelated cwd, unchanged stale
inputs, regular/symlink targets and usage errors. The existing isolated archive
probes validate runtime dependency isolation, generation imports and exact
contents, as well as repeated build hashes and private-file exclusion.

## Actual VS Code Extension Host verification

The official installed VS Code was exercised with its documented
`--extensionDevelopmentPath`/`--extensionTestsPath` integration-test interfaces,
using a disposable probe under `/private/tmp/enrama-c03-editor/`. The probe is
verification-only, is not shipped as an Enrama extension, and is not required by
clients. It used the real Red Hat YAML extension, real files and actual
`vscode.executeCompletionItemProvider`, `vscode.executeHoverProvider` and
`vscode.languages.getDiagnostics` results.

The native CUA binding selected the user's original Enrama window rather than
the separate test-profile process. To preserve that window/profile, verification
used the official isolated Extension Host/provider APIs instead. The editor's
visual popup/menu rendering was not manually reviewed; provider behavior was
exercised in the actual editor, not simulated with a standalone JSON validator.

The synthetic client copied the checked schema and the contract's single-folder
settings. Its separate user-data profile disabled SchemaStore auto-association
and used a refused proxy at `http://127.0.0.1:9`. No normal user settings or real
client repository were modified.

| Actual observation | Result |
| --- | --- |
| Invalid `theme.name: unknown` | Real YAML diagnostic: `Value is not accepted. Valid values: "minimal", "bold".` at zero-based line 8 |
| Theme value completion | Actual completion labels `bold`, `minimal` |
| Hover on `site` | `SiteConfig` and model text: `Document metadata; a public base URL is optional for local work.`, with a local schema source link |
| Remote negative control | Replacing the mapping with an HTTPS schema produced a proxy connection failure at `127.0.0.1:9` |
| Local mapping restored under the same blocked proxy | Local schema validation resumed with its expected theme diagnostic |
| Explicit `/custom.yaml` association | Same structural diagnostic on the alternate selected filename |
| Unrelated YAML | No Enrama schema/version/theme diagnostics from the root-file mapping |

The final probe completed successfully with **seven positive checks**. An early
hover probe serialized lazy MarkdownString objects as `{}` and timed out despite
an actual hover response; resolving/reading the returned contents produced the
model text above. No product change was needed for that probe correction.
This proxy-controlled result demonstrates that the Enrama schema needs no remote
fetch; it does not claim all VS Code networking was disabled system-wide.

Raw result JSON, probe source and logs are retained locally in
`reports/c03/editor/` (ignored). The synthetic client README records its exact
source revision and schema digest. No editor test result is inferred from merely
parsing the settings JSON.

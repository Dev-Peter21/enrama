# C01 verification

Status: **local implementation verified on `develop`**, 2026-10-23, awaiting
maintainer acceptance of [issue #5](https://github.com/Dev-Peter21/enrama/issues/5).
The [accepted YAML v1 contract](../configuration.md) is the behavior specification;
the [implementation plan](../superpowers/plans/2026-10-23-c01-models.md) records scope.

## Delivered behavior

- Six importable Pydantic models under `enrama.config`, with strict types,
  forbidden extra keys, explicit defaults/null policy, text limits, theme colors,
  per-collection limits, and globally unique IDs including disabled entries.
- URL validation with field-specific schemes, restricted contact URI forms,
  preservation of accepted input, and no network/reachability checks.
- Registered language/script/region/variant validation with casing-only
  normalization, no alias repair, and fixed offline registry data.
- Portable lexical client asset references without reading/resolving client files.
- Nine social presentation mappings and twelve general-icon identifiers; social
  domains remain unrestricted within the HTTPS policy. No SVGs are bundled.
- Exact package inclusion extended for these modules and the `py.typed` marker;
  no client data, caches, unrelated source files, or developer tools in the
  installed runtime.

YAML loading/diagnostics, generated JSON Schema, asset existence/format/symlink
checks, rendering/escaping/metadata, CLI, and themes remain later issues. Tests
that accept plain text are not rendering escape tests. The package version
remains `0.1.0.dev0`; no PyPI upload, release, or deployment was performed.

The language validator reads that trusted installed package resource once at
module import, then uses in-memory sets indexed by IANA subtag type. It excludes
private-use entries/ranges and preserves deprecated registered identifiers.
It does not use langcodes' permissive alias normalization or broad CLDR validity
pattern. Registrations newer than this fixed snapshot are not automatically
accepted; updating the snapshot requires an intentional dependency/data change.
No data updater or runtime registry download is implemented.

## Local checks actually executed

The existing baseline suite passed **17 tests** before implementation.
Test-first checks observed missing validation modules (118 failures), then
missing model exports (165 failures), and finally missing model modules in the
old wheel/sdist inclusion rules (three distribution failures). Contact URI
boundary tests also exposed header-parser exceptions, accepted comments/spaces,
and empty tel query/fragment delimiters; these were corrected before delivery.

The final local verification ran:

```console
uv sync --locked
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy src tests scripts
uv run --locked pytest --junitxml=reports/pytest.xml -q
uv build --python 3.12 --build-constraint build-constraints.txt --require-build-hashes
```

All passed: **313 tests**, comprising **122 validator cases**, **174 model cases**,
and the **17 existing integration cases** (with distribution probes extended for
C01). Strict mypy checked 13 source files. Both constrained archives were built.
uv's existing experimental build-hash warning remains informational.

The wheel and sdist are each installed into a separate fresh consumer environment
outside the checkout. Each consumer uses Python `-I`, imports the real installed
models, validates language/defaults/contact/social/image data, and rejects an
invalid boolean schema version with field context. After imports and metadata
reads, an audit hook rejects file opens and socket operations during these model
validation calls. Thus the missing client avatar remains a lexical reference,
not a filesystem lookup, and validation uses no network service.

Archive tests compare repeated-build hashes and exact file inventories while
rejecting synthetic private files. Runtime requirements are the two declared
libraries; dependency installations exclude pytest, Ruff, mypy, Hatchling, uv,
PyYAML, Typer, Jinja2, and FastAPI. No CLI entry point exists.

## CI and review evidence

The existing F03 workflow and matrix are unchanged. Its next run must execute
Linux/Python 3.12–3.15 plus macOS/Windows 3.12; local Python 3.12 results alone do
not establish those environments. Remote run results will be recorded once available; no unexecuted matrix check
is claimed here.

An independent read-only review covered `b0c0754..79fd97c` and independently ran
all 287 then-existing unit cases. It found no Critical findings and one Important
finding: Windows normalizes `dist./logo.png` to the reserved output tree. Nine
new regressions through avatar/favicon/OG image fields first failed, then passed
with a portable lexical rejection of the alias (mixed case and both separators).
The full suite after the correction passes 313 tests, with no deferred Minor
findings. The review correction is verified by regressions rather than a second
review. Windows normalization reference: [Microsoft path formats](https://learn.microsoft.com/en-us/dotnet/standard/io/file-path-formats#trim-characters).

The review also confirmed these scope boundaries:

- DNS reachability is intentionally unchecked; structurally valid destinations
  can be unreachable. Unusual hosts still pass through the HTTP URL parser.
- Variant-prefix compatibility is not an added language rule; registered,
  unique variants follow the accepted subset even for unusual combinations.
- Missing files, symlinks, formats, devices, and actual filesystem usability are
  G01 work; an accepted model is not proof that every asset can be built.
- Models are not immutable or assignment-validated; direct Python mutation after
  validation is not a fresh validation operation. Callers must revalidate inputs.
- The independent review did not execute remote CI; the delivery must obtain
  actual matrix evidence separately rather than treating local success as it.
- Work commits directly to `develop` under the explicit maintainer instruction;
  no integration into `main` or PR is implied.

Issue #5 remains open for maintainer acceptance. No Done transition or milestone
completion is implied by this verification record.
